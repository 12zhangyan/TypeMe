## 一、冻结的接口（实现代理之间的契约，不得擅自更改）

> ⚠️ 三个代理按下面的契约各自实现。**任何一方想改契约，必须先停下来报告，不能自行改。**

### 1.1 题库 YAML：`backend/src/main/resources/content/questionnaire-quick.yml`

```yaml
version: "quick"
title: "快速版"
questionCount: 32
estimatedMinutes: 5

# 计分常量：每维一个常数，判定阈值为 midpoint（判定用 > midpoint，不是 >=）
scoring:
  midpoint: 24
  constants:
    EI: 30
    SN: 12
    TF: 30
    JP: 18

questions:
  - id: 1                 # 原官方题号，必须与 OEJTS 1.2 PDF 的 Q1..Q32 完全一致
    textLeft: "喜欢列清单"   # 圈 1 的一端（官方左端）
    textRight: "凭记忆"      # 圈 5 的一端（官方右端）
    dimension: "JP"        # EI | SN | TF | JP
    direction: 1           # +1 | -1，官方计分公式中该项的符号
```

**计分规则（由前端实现）**：

```
score(dim) = constants[dim] + Σ over questions of (direction_i × answer_i)
answer_i ∈ {1,2,3,4,5}，5 = textRight 端
```

**已验算的常量表（必须一致）**：

| 维度 | 常量 | 参与题号与符号 |
|---|---|---|
| EI | 30 | Q3−, Q7−, Q11−, Q15+, Q19−, Q23+, Q27+, Q31− |
| SN | 12 | Q4+, Q8+, Q12+, Q16+, Q20+, Q24−, Q28−, Q32+ |
| FT | 30 | Q2−, Q6+, Q10+, Q14−, Q18−, Q22+, Q26−, Q30− |
| JP | 18 | Q1+, Q5+, Q9−, Q13+, Q17−, Q21+, Q25−, Q29+ |

> 上表展开后**必须**等于官方原文的 4 条公式。任一符号或常量不符即为 bug。

### 1.4 REST API（前缀 `/api/v1`，全部 GET，无写接口）

| 端点 | 返回 |
|---|---|
| `GET /meta` | `{appVersion, contentVersion, questionnaireVersions[], attribution{...}}` |
| `GET /questionnaires/{version}` | `{version, title, questionCount, estimatedMinutes, scoring{midpoint,constants{}}, questions[]}` |
| `GET /types/{code}` | 1.2 的单个类型对象 |
| `GET /method` | 1.3 的内容 |
| `GET /actuator/health` | 健康检查 |

**前端契约**：`GET /questionnaires/{version}` 返回的 `scoring` 与 `questions` **必须原样驱动计分**——前端**不得硬编码**题号、符号或常量。

### 1.5 前端 TS 类型（`frontend/src/domain/types.ts`，由前端代理提供）

```ts
export type Dimension = 'EI' | 'SN' | 'TF' | 'JP'
export type Pole = 'E' | 'I' | 'S' | 'N' | 'T' | 'F' | 'J' | 'P'

export interface Question {
  id: number
  textLeft: string
  textRight: string
  dimension: Dimension
  direction: 1 | -1
}

export interface ScoringConfig {
  midpoint: number
  constants: Record<Dimension, number>
}

export interface Questionnaire {
  version: string
  title: string
  questionCount: number
  estimatedMinutes: number
  scoring: ScoringConfig
  questions: Question[]
}

export type Clarity = 'A' | 'B' | 'C' | 'D'

export interface DimensionResult {
  dimension: Dimension
  score: number          // 8..40
  intensity: number      // 0..100
  dominant: Pole
  secondary: Pole
  clarity: Clarity
  distance: number       // |score - midpoint|
}

export interface QuizResult {
  typeCode: string       // 如 "ISFP"
  dimensions: DimensionResult[]
}
```

**B5 必须包含的断言**：

> ⚠️ **勘误（2026-09，由前端代理发现，已验算确认）**：本节初版误写「全选 1 → 每维 8 分 / 全选 5 → 每维 40 分」。**那是错的**——它是照「8 题原值直接相加」的错误算法（即 `openjung` 的 bug）倒推出来的。
>
> 官方公式下每维的**符号和**为：EI −2、SN +4、TF −2、JP +2。因此：

| 输入 | EI | SN | TF | JP | 期望类型 |
|---|---|---|---|---|---|
| 全部选 1 | 30−2 = **28** | 12+4 = **16** | 30−2 = **28** | 18+2 = **20** | **ESTJ** |
| 全部选 3 | **24** | **24** | **24** | **24** | **ISFJ**（因判定是 `>24`） |
| 全部选 5 | 30−10 = **20** | 12+20 = **32** | 30−10 = **20** | 18+10 = **28** | **INFP** |

**极值 8 / 40 要用专门的作答模式来测**（不是"全选 1 / 全选 5"）：

| 目标 | 作答方式 |
|---|---|
| 每维 8 分（下界） | **负号题选 5、正号题选 1** |
| 每维 40 分（上界） | **负号题选 1、正号题选 5** |

| 不变量 | 任意作答下每维得分恒在 `[8,40]`；`intensity ∈ [0,100]` |
|---|---|

## 三、必须避免的三个陷阱

### ⚠️ 陷阱 1：左右端被交换（最致命）

题库的 `textLeft` 必须对应官方 PDF 中**圈 1** 的一端，`textRight` 对应**圈 5** 的一端。

**如果翻译时把左右两端写反，`direction` 的符号就整体反转，结果会系统性出错**——而且是那种"看起来能跑、结果全错"的 bug。

**对策**：以 `research/_sources/OEJTS1.2.txt`（官方 PDF 提取文本）和 `research/01-题库来源.md` §A1 的表格为唯一依据，逐题核对左右顺序；不要依赖任何第三方中文译本。

### ⚠️ 陷阱 2：把常量硬编码到前端

常量与符号必须来自接口返回的 `scoring` 与 `questions[].direction`。前端硬编码会导致题库一改就错。

### ⚠️ 陷阱 3：判定写成 `>=`

官方是 **`> 24`**，中点 24 归到 **I / S / F / J** 一侧。写成 `>=` 会让"全选 3"得到 ENTP 而不是 ISFJ。

> 这三条正是 `openjung/core` 翻车的地方（它把 8 题原值直接相加判 `>24`，丢了符号和常数）。

## 五、审查计划（package 模式）

实现代理全部返回后，派出**相互独立的只读 reviewer**，各自独立取证、不写代码：

| Reviewer | 焦点 |
|---|---|
| R1 | **计分正确性**：独立按官方 PDF 重算 4 条公式，逐题核对 `direction` 符号与常量；用三组极端输入独立验算 |
| R2 | **题库内容**：逐题核对左右端顺序与官方一致（陷阱 1）；中文表达质量；有无翻译腔 |
| R3 | **后端契约与校验**：ContentService 校验是否真能在内容被改坏时失败；API 是否符合 1.4；SPA 回退是否正确 |
| R4 | **前端与降级**：类型安全、localStorage 续答、后端不可用时的降级、canvas 分享图、移动端/微信可用性 |
| R5 | **合规与文案红线**：CC BY 署名是否出现在落地页与关于页；是否出现"最准/官方/诊断"等红线词；是否输出了人群百分位 |

**聚合规则**（package 模式）：合并同一根因、保留来源别名；accepted finding 归一为 `CR/IM/MI`；误报/无证据归 `RJ`；待业务裁决归 `BK`。**至少 2 个 reviewer 成功返回才算多 reviewer 结果**，否则披露覆盖边界。
