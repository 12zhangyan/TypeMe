## 1. 标识与版本

| 名称 | 值 | 说明 |
|---|---|---|
| instrument.id | `typeme-jung48` | 新仪器，独立于 `oejts32` / `ipip50` |
| packageId | `typeme-jung48-zh-v1` | 内容包（64 题 + 维度解释 + 报告政策），发布后不可改 |
| scoringVersion | `typeme-jung48-score-v1` | 计分规则版本 |
| reportContentVersion | `typeme-type-report-zh-v1` | 16 型基础报告内容版本，独立于内容包 |
| 维度顺序（权威序） | `EI`, `SN`, `TF`, `JP` | 任何输出数组都按此序，不按字典序 |

### 1.1 极点（pole）与正负极

统一约定：**每维第一个字母为负极，第二个字母为正极**。

| 维度 | 负极（negative） | 正极（positive） | 说明 |
|---|---|---|---|
| EI | `I` | `E` | 与 OEJTS 相同 |
| SN | `S` | `N` | 与 OEJTS 相同 |
| TF | `T` | `F` | **与 OEJTS 相反**（OEJTS 的数值高侧是 T）。禁止复用旧符号常量 |
| JP | `J` | `P` | **与 OEJTS 相反** |

极点是**字符串枚举**，不是数组下标，也不是布尔值。题目用 `leftPole` / `rightPole` 显式声明，
取值必须是同一维度的两个极点且互不相同（合法配对只有 `I/E`、`S/N`、`T/F`、`J/P`）。

### 2.1 题号规则（可校验）

- 主测：`{DIM}-{01..12}`，例如 `EI-07`。
- 澄清：`{DIM}-C{1..4}`，例如 `TF-C3`。
- `id` 全局唯一；`order` 在包内全局唯一，主测 1..48（按维度轮转），澄清 49..64。

### 2.2 主测排序（用户体验）

主测 `order` 按**维度轮转**排列：`EI-01, SN-01, TF-01, JP-01, EI-02, SN-02, ...`，
即每 4 题一轮，避免连续 12 题问同一件事。

### 2.3 左右平衡（生成期校验，必须通过）

每维主测 12 题中，`leftPole` = 负极的 6 题、`leftPole` = 正极的 6 题；
澄清 4 题中各 2 题。**校验器必须拒绝不平衡的包**（防止"一直点左边"造成系统偏差）。

### 2.4 发布期校验清单（`ContentValidationException` 逐条报错）

1. `packageId`/`instrument.id`/`scoringVersion` 与注册表白名单一致。
2. 主测每维恰好 12 题，澄清每维恰好 4 题，总数 64。
3. 全部 `id` 唯一；`order` 唯一且连续 1..64。
4. 每题的 `leftPole`/`rightPole` 属于该题 `dimension`，且两极点不同。
5. 每维左右平衡 6:6（主测）、2:2（澄清）。
6. `help` 非空（25 字以上）；`scenario` 非空；`textLeft`/`textRight` 非空且不相等。
7. 每维覆盖 ≥3 种不同 `facet`（防止 12 题同义反复）。
8. 16 型报告内容齐备（`typeme-type-report-zh-v1`），每型含全部章节。
9. 无占位符（`TODO`、`XXX`、`……待补`、`lorem` 等）。
10. `sha256` 与实际内容一致。

## 3. 作答模型

| 概念 | 表示 | 说明 |
|---|---|---|
| rating | `kind="rating"` + `rating ∈ {1,2,3,4,5}` | 数字回答 |
| unknown | `kind="unknown"` | "暂不适用 / 无法判断"，**不计入 n**，也不计贡献 |
| 未处理 | 该 `questionId` 没有任何记录 | 与 unknown **严格区分**；服务端不得自动补 3 或补 unknown |

`rating=3` 是**有效中立**：计入 `n`，贡献 0。

## 4. 权威计分规则（scoringVersion = typeme-jung48-score-v1）

对某一题的答案记录（rating `r`）、题目维度 `d`：

```
positivePole(d) = 维度 d 的正极（EI→E, SN→N, TF→F, JP→P）
direction = +1  若 question.rightPole == positivePole(question.dimension)
            -1  否则                       // 等价于 leftPole == positivePole
c = direction × (r − 3)          ∈ {−2,−1,0,1,2}
```

对一组题集 `Q` 与答案集合：

```
n = |{ q ∈ Q : 答案 kind == rating }|          // unknown 与未处理都不计入
S = Σ c                                          // 整数
m = n == 0 ? null : S / (2n)                     // 归一化偏移 ∈ [−1,1]
p = m == null ? null : (m + 1) / 2               // 图示位置 ∈ [0,1]，仅用于画条
```

**方向只看整数 S**：`S > 0` → 正极字母；`S < 0` → 负极字母；`S == 0` → 平分（`tiedSide = "tied"`）。
不得先对 `m` 或 `p` 做四舍五入再判方向。

### 4.1 澄清触发与边界（整数规则，v1.1 冻结）

设 `n` 为该维**当前应判定的题集**里的 rating 数：

```
T(n) = floor(2n / 10)      // 触发阈值：|S| <= T(n) 需要澄清
B(n) = T(n) - 1            // 边界标记：|S| <= B(n) 判定为"倾向较轻"
```

| n | T(n) 触发 | B(n) 边界 | 依据 |
|---|---|---|---|
| 9 | 1 | 0 | 主测缺 3 题时的最保守情形 |
| 12 | 2 | 1 | `2×12/10 = 2.4`，取整 2 |
| 16 | 3 | 2 | `2×16/10 = 3.2`，取整 3 |

- **触发集合**：主测覆盖达标（见 §5.1）的每一维，若 `|S_base| <= T(n_base)`，则该维进入澄清集合。
  此时该维是"待澄清"，**尚不判定** `boundary`。
- **边界标记**：只在**最终合并题集**上判定一次：`boundary = (|S_final| <= B(n_final))`。
  即最终 `|S_final| <= T(n_final)` 但 `> B(n_final)`（恰好落在 `T` 那一格）时**不算边界**，
  状态仍可为 `REFERENCE`。
- `n = 0`（该维没有任何 rating）不触发澄清（`m` 为 null）；但该维必然违反主测覆盖条件，先走 `NEEDS_REVIEW`。

> **与开发方案 §3.4 第 4 条的差异（明示）**：开发方案样例写的是
> `5×abs(S) <= 2n`（"追加 4 题贡献 −6 → 最终 S=−2, n=16 仍标边界"）。
> 按 `5|S| <= 2n` 判定，`|−2| <= 6.4` 成立 → 边界；按本契约 `B(16)=2` 判定 `|−2| <= 2` 也成立 → 边界。
> **该样本在两种写法下结论相同**，可以照原样做夹具。
> 差异只出现在 `T(n)` 那一格（`n=12` 时 `|S|=2`；`n=16` 时 `|S|=3`）：按 `5|S|<=2n` 算作边界，
> 按本契约算作**非边界**。本契约取更严格的一侧，理由：`|S| = T(n)` 恰好是"需要追加澄清"的位置，
> 追加后仍停在该值，说明证据只够判定方向、不够支撑"较明显偏向"，因此不给边界标记。
> 实现与测试一律以本契约为准。

### 4.2 主测覆盖条件（提交前）

`POST .../submit` 的前置条件，任一不满足即 `NEEDS_REVIEW`（HTTP 200 + 该状态，不生成报告）：

1. 主测 48 题的**每一题都被处理**（rating 或 unknown 之一）。
   —— 未处理题不得被服务端自动视为 unknown。
2. 每维主测 rating 数 `>= 9`。

覆盖不足时返回 `NEEDS_REVIEW`，附带每维 `baseRatingCount` / `baseUnprocessed`，草稿保留。

### 4.3 review（固定澄清题集合）

`POST .../review` 由服务端计算：

```
needsClarification = []
for d in [EI, SN, TF, JP]:
    if baseRatingCount(d) >= 9 and abs(S_base(d)) <= T(n_base(d)):
        needsClarification.push(d)
```

- 结果是**维度列表**，按 `EI,SN,TF,JP` 序。
- 服务端把该列表写入 attempt 的 `clarification_dimensions`（幂等：重复 review 返回同一列表，
  不重复"建题"；已安排题目集合 = 该维度固定 4 题）。
- 客户端**不能**自行指定澄清题集合；提交时服务端重新计算并校验：
  - 已安排维度的 4 题：每一题都必须被处理（rating 或 unknown）。
  - 未安排维度的任何澄清题：出现即 `400 INVALID_REQUEST`（不能自由挑有利题目）。
  - 若用户选择跳过：`clarificationSkipped = true`，允许已安排题目保持未处理。

### 4.4 最终合并（等权）

```
QFinal(d) = { 主测 d 的 12 题（已处理） } ∪ { 澄清 d 的 4 题（仅当该维被安排） }
n_final = |{ q ∈ QFinal(d) : rating }|
S_final = Σ c over QFinal(d)
m_final = S_final / (2 n_final)
```

- 澄清题**不替代**主测覆盖条件（§4.2 的先决条件）。
- 一轮澄清，最多 16 题；**不再触发第二轮**（`T(n_final)` 只用于边界标记，不再追加题目）。
- 必须同时保留分项：`nBase/SBase/mBase`、`nClar/SClar`。

## 5. 结果状态与类型

### 5.1 状态判定（按此顺序）

| 顺序 | 条件 | status | computedTypeCode |
|---|---|---|---|
| 1 | 违反 §4.2 覆盖条件 | `NEEDS_REVIEW` | `null`（不生成报告） |
| 2 | 任一维 `S_final == 0` | `TIED` | `null` |
| 3 | 四维 `S_final != 0`，且至少一维 `boundary == true` | `TENTATIVE` | 四字母 |
| 4 | 其余 | `REFERENCE` | 四字母 |

`boundary` 按 §4.1 在**最终题集**上判定。

### 5.2 类型码格式

- 严格匹配 `^[EI][SN][TF][JP]$`。
- `IMFJ`、`XXXX`、`ENFP `（带空格）、`enfp`（小写）在**服务端一律拒绝**（`400 INVALID_TYPE_CODE`）；
  服务端自己产生的类型码恒为大写规范形。
- 客户端传入的任何 `typeCode` 一律忽略/拒绝：类型只由服务端计分产生。

### 5.3 边界维度的展示

`TENTATIVE` 时，对每个 `boundary == true` 的维度给出该维的 `m_final` 与两个极点字母，
文案形如"本次略偏 E（倾向较轻），也可以一起看看 INFP 的差异"。**不得**隐藏整个类型，
**不得**输出准确率/概率/百分位。

## 6. 候选类型

候选仅在 `status != REFERENCE` 时生成。

```
for d in [EI, SN, TF, JP]:
    if S_final(d) == 0:                    // 平分：两极成本相同，两个都进候选
        choices(d) = [negativePole(d), positivePole(d)]
    elif boundary(d):                      // 边界：计算极 + 相反极
        choices(d) = [computedPole(d), opposite(computedPole(d))]
    else:
        choices(d) = [computedPole(d)]     // 非边界：固定
候选 = choices(EI) × choices(SN) × choices(TF) × choices(JP)     // 1..16 个
```

每个候选的距离（**不是概率**）：

```
cost(candidate) = Σ_d |S_final(d)|  对于所有 candidate.pole(d) != computedPole(d) 的维度
                + 0                 若 candidate.pole(d) == computedPole(d)
```

- `S_final(d) == 0` 的维度无论选哪极都记 0（因为 `|S| = 0`）。
- **排序**：`cost` 升序；`cost` 相同时按维度顺序 `EI,SN,TF,JP` 依次取
  `computedPole` 优先（平分维取 `negativePole`）作为稳定次序。
- **平局语义**：`cost` 相同的候选互为并列。排序**只用于稳定展示**，不得让字典序产生"最可能"的暗示。
- `tiedDimensions`（`S_final == 0` 的维度列表）长度 `>= 2`，或候选数 `> 1` 且最小 cost 有并列时：
  - 顶层给出 `tieNotice`，文案说明"这些候选在本次数据里没有区别"。
  - 前端**不得**把第一个候选渲染成主结果、大标题或分享主标题。
- 首屏最多展示 3 个候选 + "查看其他候选（共 N 个）"；N 最大 16。

### 6.1 自我选择（与问卷结果隔离）

- `selfSelectedTypeCode` 独立存储（`report_self_reflection` 表），必须匹配 §5.2 格式。
- 不覆盖 `computedTypeCode`、`score_json`、`reportHash`。
- 存在自我选择时，报告以"问卷参考 / 我的自我理解"两栏并列呈现。
- AI 输入默认只使用问卷结果与候选。

### 7.1 过程层（`dynamics` / `processPlan`）

方法论与被引章节见 [`../TypeMe-分析建议方法论-v2.md`](../TypeMe-分析建议方法论-v2.md)。
要点：**这一层不引入任何新的测量**，它完全由四个字母决定 —— 同一份作答换个实现跑，
字母一样、结构就一样。因此报告里必须同时展示"这是推导"的说明（`basis` / `notes.frameworkCaveat`），
否则用户会把它读成"另一个测试结果"。

```jsonc
"dynamics": {
  "version": "typeme-jung48-dynamics-v1",
  "typeCode": "ISTJ",                        // 必与顶层 computedTypeCode 相同
  "rule": "……",                              // 为什么是这四个过程（逐条对照字母讲）

  "processes": [                             // 恰好 4 项，slot 顺序固定
    { "slot": "dominant",  "order": 1, "process": "Si", "function": "S", "attitude": "i",

    { "slot": "auxiliary", "order": 2, "process": "Te", "function": "T", "attitude": "e",
      "nameCn": "外倾思考", "roleTitle": "辅助过程", "what": "……", "reading": "……",

    { "slot": "tertiary",  "order": 3, "process": "Fi", "function": "F", "attitude": "i",

    // 注意：这里必须写**真实后果**并点名换过去的过程。E/I 换边是"同一套四个过程、主辅互换"；
```

`slot` 依次为 `dominant` / `auxiliary` / `tertiary` / `inferior`，`order` 与数组位置一致。
`processes[i].preferred` 只对前两位为 `true`。四个过程**恰好各占 S/N/T/F 之一**（构造期校验）。

> **读端（前端）必须按 `methodology.dynamicsVersion` 判别新旧快照，不能只看 `computedTypeCode`。**
> 只看四字母会把两件不同的事混成一件：**新报告漏发字段**（bug）与**过程层上线前的旧报告没有这个字段**
> （正常历史数据）。判别规则与理由见
> [`03-AI与前端契约-v1.md`](03-AI与前端契约-v1.md) §7.3 —— 简言之：有 `dynamicsVersion` 时严格全开，
> 没有时两块读成 `null`、不渲染、不报错；但**无论哪种情况，"只给一半"都必须抛错**（那是真损坏）。

```jsonc
"processPlan": {
  "version": "typeme-jung48-dynamics-v1",
  "developmentOrder": [                      // 恰好 3 段，顺序不可改（原书 19.2 的三层要求）
    { "order": 1, "title": "先把主导过程用熟", "body": "……",

    { "order": 2, "title": "让辅助过程承担对外的事", "body": "……", "processes": [ /* 1 项 */ ] },

      "processes": [ /* 2 项，并列、不分先后 */ ] }
  ],
  "decisionIntro": "……",
  "decisionSteps": [                         // 恰好 4 步，function 顺序固定 S → N → T → F
    { "order": 1, "function": "S", "title": "先用感觉处理事实", "prompt": "……",
      "slot": "dominant", "slotTitle": "主导过程", "process": "Si",
      "preferred": true, "how": "这一步对应你的主导过程（Si），用起来最省力。" }
  ],
  "decisionNote": "……",
  "hardestSteps": ["……", "……"],              // 恰好 2 条：decisionSteps 里 preferred=false 的那两步
  "hardestStepsNote": "……",
  "opposites": [                             // 恰好 2 条：SN 与 TF（原书图表 32 的口径）
    { "axis": "SN", "axisName": "信息关注", "yourPole": "S", "needPole": "N",
      "need": "你需要偏直觉的一侧提供：……", "supply": "你能提供给偏直觉的一侧：……" }
  ],
  "communicationRules": [                    // 恰好 4 条，axis 顺序固定 EI → SN → TF → JP
    { "axis": "EI", "axisName": "精力方向", "title": "关于精力的给与取",
      "yourPole": "I", "body": "……" }
  ],
  "notes": { "developmentNote": "……", "greyAreaNote": "……" }

```

**为什么第 3 段的发展任务里两个过程并列**：原书 19.2 只给了三层要求，并未在第三层内排序；
而且作者明确撤回了她早年"发展必须按时间表完成"的假设（p.194）。
报告里只有"第四位是发展得最不充分的那一个"这一条**过程之间的**次序说明，并紧跟一句"这不是年龄表"。

**`reportHash` 的产生方式**：`JungReportBuilder.build(...)` 返回的 map **不含** `reportHash`；
落库前必须调用 `JungReportBuilder.finalizeWithHash(mapper, report)`，由它先序列化、算哈希、
追加字段、再序列化。设计成"必须先序列化一次"是因为哈希要覆盖除自己以外的全部字段，
所以不能一边算一边塞。这一步收在 Builder 里而不是调用方，是为了让
"两次序列化之间不许插字段"这个不变量只由一处代码负责。

`typeSections` 的 key 固定为：

| key | 标题 |
|---|---|
| `dailyLife` | 日常表现 |
| `strengths` | 可能用得顺手的地方 |
| `blindSpots` | 容易卡住的地方 |
| `communication` | 沟通与关系 |
| `studyWork` | 学习与工作方式 |
| `stress` | 压力下的观察 |
| `growth` | 成长行动 |
| `neighbors` | 相邻类型区别 |

`share.kind` 与 `status` 一致；`TIED` 时 `share.headline` 必须是"几个类型都值得看"之类，
**不得**出现任何一个候选四字母作为主标题。

## 8. 权威计分服务接口（Java 侧）

新测计分必须与旧引擎物理隔离。**不要改** `com.typeme.service.ContentService` 与既有 v1/v2 控制器。

```
com.typeme.jung.content
    JungPackageLoader        // 读 typeme-jung48-zh-v1.yml + typeme-type-report-zh-v1.yml，启动期校验
    JungPackage              // 不可变内容包（questions 索引、dimensions 索引、scoringPolicy）
    JungQuestion             // id, stage, dimension, leftPole, rightPole, facet, order, ...
    JungDimensionPolicy      // dimension, negativePole, positivePole, name, ...
    JungScoringPolicy        // scoringVersion, minBaseRatingsPerDimension, boundaryNumerator/Denominator

com.typeme.jung.domain
    enum JungDimension { EI, SN, TF, JP }        // 有序：EI, SN, TF, JP
    enum JungPole { I, E, S, N, T, F, J, P }
    record AnswerRecord(String questionId, Kind kind, Integer rating)   // Kind = RATING | UNKNOWN
    enum JungResultStatus { NEEDS_REVIEW, TIED, TENTATIVE, REFERENCE }

com.typeme.jung.scoring
    final class JungScorer                       // 纯函数，无 Spring、无 IO、无时间
        static JungScoringResult score(JungPackage pkg, Map<String, AnswerRecord> answers, boolean clarificationSkipped)
        static List<JungDimension> reviewClarification(JungPackage pkg, Map<String, AnswerRecord> answers)
        static CoverageCheck checkCoverage(JungPackage pkg, Map<String, AnswerRecord> answers)
```

`JungScorer` 约束：

- 只接收 `packageId` 已锁定的 `JungPackage`；**不读文件、不读数据库、不取当前时间**。
- 输出里的顺序恒为 `EI, SN, TF, JP`。
- `NEEDS_REVIEW` 时仍返回每维的 `coverage`（`baseRatingCount`、`baseUnprocessed`），且 `report == null`。
- 必须能被同一份 JSON fixtures 驱动（见 §10）。

`JungReportBuilder`（`com.typeme.jung.report`）把 `JungScoringResult` + `typeme-type-report-zh-v1`
内容拼成 §7 的 `report_json`，并计算 `reportHash`（对**去掉 reportHash 字段后**的规范化 JSON 求 sha256）。

## 11. 前端预览 vs 后端权威

- 前端 `frontend/src/domain/jungScore.ts` 是 `JungScorer` 的**TypeScript 同构实现**，只用于：
  答题页实时进度与草稿回显、离线预览、单元测试。
- **提交参数绝不含客户端算出的分数或类型**；只发答案与 `expectedRevision`。
- 报告页**只读** `GET /api/v3/reports/{id}` 返回的 `report_json`，本地不再重算。
- 两者必须通过 §10 的同一份夹具得到相同结论；夹具不一致时以 Java 为权威并修 TypeScript。
- 同理，`frontend/src/domain/jung/dynamics.ts` 是 §7.1 过程层的 TS 镜像，**只用于本地校验与测试**：
  过程结构由服务端算好并连文案一起写进 `report_json`，前端**不得**用它覆盖服务端结果。
