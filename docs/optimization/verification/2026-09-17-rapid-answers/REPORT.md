# 探索性 QA：快速连点是否会**伪造**出「另一台设备」冲突（2026-09-17，第 15 轮）

- 被验收地址：`http://127.0.0.1:5174`
- 使用账号：`rapid_3e42758a`（密码为脚本生成的合成值，未记录）
- 结论：**未复现，而且找到了未复现的真正原因**（PASS 10 / FAIL 0）

## 假设 H1

`AssessView.chooseRating()` 先写本地答案、再 `await flush()` 发 PATCH；
`[data-next]` 只按 `submitting || loading` 禁用、**不看 `saveState`**，选项也没在
保存期间禁用。所以快速连点两下 = 两个带**同一个** `expectedRevision` 的 PATCH，
服务端 `AttemptService.patchAnswers:196` 必然让第二个 409。
而前端把任何 409 都翻译成「另一台设备已经改过这份进度」，并进入阻断态。

## 观察记录（含请求体取证）

| 场景 | PATCH 数 | expectedRevision | 响应码 |
| --- | --- | --- | --- |
| Playwright 连点（有稳定性检查，较慢） | 2 | `[0, 1]` | `[200, 200]` |
| 同一 JS 回合内连点两档 | 2 | `[2, 2]` | `[200, 200]` |
| 同一 JS 回合内『选一档 + 下一题』 | 2 | `[3, 3]` | `[200, 200]` |

同回合那两组的请求体是：

- 连点两档：`题目=[['EI-01'], ['EI-01']]`、`档位=[[1], [5]]`
- 选完即下一题：`题目=[['EI-01'], []]`（第二个只带 `currentQuestionId`）

**关键取证**：连点两档那一步，第一次点击之后读到的保存文案已经是「已保存」，
说明**第一次保存已经在第二次点击之前完成了** —— 两个 PATCH 是**串行**的，
不是并发。本地往返只有十几毫秒，所以"同一个 JS 回合"并不等于"两个请求重叠"：
第二个请求是在第一个响应回来、`this.revision` 已更新之后才构造的。

## 结论：假设不成立（在当前网络的时序下），但代码里的窗口是真的

- `flush()` 确实**没有串行化**：`expectedRevision` 在请求体构造时同步取值，
  而 `this.revision` 只在 await 成功后更新。只要两个 `flush()` 真的重叠
  （高延迟网络、慢接口），就会发出两个同 revision 的 PATCH，第二个必然 409，
  并被前端翻译成「另一台设备改过这份进度」。
- 我**没能**在本地把这个窗口撑开：请求处理器里不能调 `page.evaluate()`
  （会让 Playwright 同步 API 死锁），而 run-to-run 的时序无法从外部确定性构造。
- 服务端那条冲突检测本身还有一个**独立的弱点**（`AttemptService:299-306`）：
  它丢弃了 UPDATE 的受影响行数，改用"另查一次 `COUNT(*) WHERE revision = 新版本号`"
  来推断自己有没有成功。而那个 COUNT 只能证明**有人**把 revision 推到了该值 ——
  真并发时另一个请求的提交也会被数进去，于是"自己一行都没改到"会被判成成功。
  正确的做法是用 UPDATE 的受影响行数。这一条我**没有改**（无法确定性复现，
  且改动会触碰乐观锁语义这个核心不变量），只记录在此。

## 本脚本的边界

- **不消耗 AI 额度**：全程只用注册 / 建测评 / 作答保存三个接口。
- 只在**单个**浏览器上下文里操作，因此任何「另一台设备」提示都必然是伪造的。
- 用的是脚本注册的一次性合成账号，作答为固定选项，不含真实个人信息。
- **本脚本无法证明"永不会发生"**：它只能证明在当前机器与本地网络下没出现。
  要真正排除这条竞态，需要人为注入延迟（节流到 3G）或改成真并发调用。
