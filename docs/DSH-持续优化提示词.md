# TypeMe 持续优化目标提示词

复制下方整段交给 DSH。它用于在现有实现上持续迭代；不是从零重新开发的提示词，也不创建后台定时任务。

```text
你现在负责持续优化 TypeMe 项目，工作目录为 D:\develop\develop\code\TypeMe。

总目标：把当前项目逐步打磨成页面清晰、移动端顺手、前后端衔接完整、业务结果可信且可以验证的中文人格参考测评站。重点是前端页面和后端业务逻辑。请实际检查、修改、运行验证并继续改进，不要只给审查报告、建议清单或下一步计划。

一、先理解已有工作

先阅读根目录 AGENTS.md，查看 git status 与相关 diff，保护所有已有修改和未跟踪文件。在已有实现上增量推进。

阅读 README 顶部的新测说明，以及以下文档中与当前问题相关的部分：
- docs/2026-09-16/TypeMe-MBTI测评站-产品方案.md
- docs/2026-09-16/TypeMe-MBTI测评站-开发方案.md
- docs/2026-09-16/implementation/_contracts/
- docs/2026-09-16/TypeMe-分析建议方法论-v2.md
- docs/2026-09-16/implementation/README.md
- docs/2026-09-16/verification/acceptance-evidence.md

主流程是 typeme-jung48 登录版测评：注册/登录 → 48 题作答 → 必要时补充 → 固定报告 → 历史回看与账号数据管理。旧 IPIP-50 / OEJTS 流程保持兼容。AI 是可选能力，不能成为基础报告的前置依赖。

当前代码、接口响应和运行证据用于确认实际状态；产品方案与契约用于确认预期。历史文档提到的缺口和通过次数都需要重新核实。不要重做已经完成的功能，也不要把旧测试结果当成本轮验收。

二、主动寻找并解决高价值问题

按真实用户路径检查页面和接口，维护一个按影响排序、带证据的问题清单。优先处理：
1. 安全边界、错误业务结果、数据丢失、主流程阻断。
2. 页面与后端口径冲突、状态不同步、保存/提交/恢复异常。
3. 高频页面的操作成本、信息层级、移动端与无障碍问题。
4. 在现有契约内补齐对用户有价值的功能，再处理有实测依据的性能与维护问题。

前端重点：
- 首页完整说明当前测什么、多少题、是否需要登录、数据保存在哪里；核查首屏到页脚，避免新测入口混入旧大五文案。
- 登录、注册、恢复与会话失效后的返回路径清楚，校验和错误提示能指导下一步，不泄露账号信息。
- 答题时题面、选项、帮助、进度和主按钮层级清晰；中间档、说不好、未回答区分明确。
- 保存中、保存失败、重试、跨设备冲突有准确反馈；快速连点、回退、刷新、切页和网络恢复不丢答案、不冒称保存成功。
- 报告用自然中文解释结果与限制，分清确定方向、略偏、平分与信息不足；历史、详情、分享和导出保持一致。
- 账号数据管理与危险操作交互清楚，空态、错误态、加载态完整。
- 复用现有视觉体系改善留白、字号、对比度、控件尺寸、长内容排版、键盘焦点和响应式，不依靠大面积装饰掩盖流程问题。
- 对修改的页面在 320、390、1440 宽度实测，检查滚动、遮挡、横向溢出和关键按钮可达性，保存脱敏截图和复现步骤。

后端重点：
- 从真实页面请求追踪到控制器、服务、持久化和响应，排查参数校验、权限归属、错误码、状态机与事务边界。
- 检查草稿保存、revision 冲突、重复创建/提交、补充题安排、覆盖不足、报告生成与历史读取；重试不产生重复业务结果，冲突不静默覆盖。
- 保持 Java 服务端计分与 TypeScript 预览一致，补充边界、极性、unknown、平分和有效题数不足的回归验证。
- 检查内容版本、报告哈希、历史不可变性和分享模型一致性。
- 检查认证、CSRF、会话过期、恢复码消费、限流、数据归属与导出/删除链路；修复时不能降低安全约束。
- 检查 AI 关闭/失败/超时/重试/取消时的状态与前端展示；基础测评独立可用，不实际调用未授权的外部模型。
- 若发现查询或并发问题，用可复现证据决定优化，不凭猜测增加缓存、依赖或复杂架构。

历史记录中提过首页下半部分口径混杂、窄屏可用性、AI 前端、报告对比、离线保存及免责声明流程等缺口。这些只是核查线索，不是认定仍存在的缺陷。先看当前实现；在产品方案与现有契约明确时完成闭环，语义不明确或需要扩大范围时再提出具体选择。

三、持续迭代的工作方式

每轮按“核实问题 → 明确改善后的行为 → 实施前后端改动 → 验证 → 更新记录 → 选择下一项”推进。

无需机械地固定每轮任务数或模块比例。围绕同一用户场景完成必要的前后端衔接；一次改动保持可审阅。复杂改动先简短说明方案、影响与验证方式，已有授权内直接继续，不要每修完一个文件就等待确认。

对新发现的失败先判断是本轮引入、原有问题还是环境限制，记录证据。修复后验证原问题消失，并检查相邻场景。不能通过删测试、放宽断言、跳过失败、硬编码示例答案或伪造 API 响应来宣称完成。

对反复失败的验证先查根因，不能无依据重复运行。测试断言应覆盖真实结果；遇到可疑的“全绿”，确认断言是否真正观察到了目标数据，必要时用受控反例验证它确实会失败。

四、验证与证据

按 AGENTS.md 选择相关命令：前端 typecheck、Vitest、完整 build；后端相关测试及适当回归；内容变化做生成与 --check；页面变化做浏览器验收。

先检查测试和启动脚本副作用。当前完整 Maven 测试包含自动在真实 MySQL 建库/删库的用例，不能在未授权时直接执行完整套件；优先已确认隔离的纯逻辑/mock/内存 H2 验证，明确报告排除范围。真实数据库联调和经业务 API 写数据需要对操作与目标的授权。

真实浏览器与 API 联调只能连接已确认的测试环境，使用获准的测试账号和合成答卷。涉及删除、注销、恢复码重置等操作，仅针对明确获准的测试对象。无法联调时继续完成代码和隔离验证，并列明尚未验证的用户路径。

如果验证整站 jar，先构建前端再打包，确认浏览器实际访问的是本轮产物。测试、打包、浏览器、真实数据库、真实 AI 和上线部署分开报告。

把持续记录放在 docs/optimization/ 下：
- backlog.md：问题、证据、影响、优先级和状态，避免多轮重复寻找同一问题。
- progress.md：每轮改动、验证命令/结果、遗留问题、下一步和所需权限。
- verification/：按日期与轮次分目录保存必要的脱敏验证证据。
记录保持简洁，服务于接续工作，不以大量文档代替实现。若已有同用途记录，优先接续。

五、边界与停止条件

本任务允许在项目内修改代码、样式、测试和文档，并执行权限范围内的本地非破坏性验证。不要擅自重写项目、换技术栈、引入依赖、变更计分政策、清除旧记录、执行数据库写操作、提交、推送、发布、部署、外部发送或消耗付费服务。

数据库默认只读；现有数据库的写入、迁移及建库删库需要具体授权。不要输出或保存真实密码、Token、Cookie、恢复码、私钥、连接串或完整个人答卷。AI 调用不外发未获准的个人数据。

已有权限内持续推进，不以“已列出建议”结束。只有以下情况才暂停：
- 已完成当前确认的高优先级问题，相关回归通过，继续改动缺少明确收益；
- 剩余事项都依赖用户的业务决定、权限或不可用环境，且独立可做的工作已经完成；
- 达到用户明确给定的时间/资源限制，或用户要求停止。

遇到单点阻塞，记录原因并先做其他独立事项；需要用户决定时给出事实、影响、推荐方案以及精确的所需操作。不要为“不断优化”无休止改动已经稳定的代码，也不要声称会在会话结束后自动继续。

上下文接近上限时，先在 progress.md 留下当前基线、修改范围、验证结果和下一步入口，后续从记录接续。结束时简洁汇报本轮实际改善、验证结果、未覆盖风险与剩余事项，不笼统声称“全部完成”。

现在开始：检查当前工作区和规则，核实主要用户路径，选出最值得先解决的问题，简述依据后直接实施第一轮，并继续推进后续有明确收益的优化。
```
