> 状态：供部署 Agent 执行的手册（未在任何服务器上执行过） ｜ 日期：2026-10-27 ｜ 基线：git main@9b47c7e 之上的未提交改动（验证码注册、前端独立部署）

## 0. 给执行 Agent 的硬规则（先读）

1. **没有用户对“具体数据库目标 + 具体操作”的授权，不得对任何数据库执行 DDL/DML、建库、删库、迁移，也不得启动后端连到现有库。** 后端启动会自动跑 Flyway、写内容包、可能创建管理员（见 §5.3），启动本身就是写库操作。
2. 不要用仓库里的开发默认值：`application.yml` 里的数据源默认值（`root` / 本机 `typeme_dev`）只用于本地开发。**服务器上必须用 `--spring.profiles.active=prod`**，该 profile 要求数据库连接全部来自环境变量、没有默认值，缺失会直接启动失败——这是想要的结果。
3. 不把真实密码、Token、密钥、连接串写进仓库、日志、截图或对话；示例文件里只有占位符。
4. 任何一步的“停止条件”触发，就停下并向用户汇报现场（命令、完整输出、退出码），不要自行“修复”（尤其不要 `flyway repair`、`DROP`、改 `flyway_schema_history`）。
5. 本手册里标 **【需授权】** 的步骤，必须先拿到用户明确同意（写清目标库和操作）。标 **【只读】** 的可直接做。
6. 仓库当前的 `mysql-readonly` MCP 连接指向的是另一套业务库，**不是 TypeMe 的库**，不要拿它查 TypeMe。

## 1. 目标拓扑

```
浏览器 ──https──> Nginx（同一域名）
                    ├─ /            → 静态文件 frontend/dist（hash 路由，无需回退）
                    └─ /api/        → 127.0.0.1:8080  后端 jar（-P api-only，只含接口）
                                          └─ MySQL 8.4（库名自定，下文用 <DB_NAME> 占位）
                                          └─（可选）AI 服务商，仅当开启 AI
```

- **必须同域**：会话 Cookie 是 `SameSite=Lax` + `Secure`，CSRF 靠 `XSRF-TOKEN` Cookie 与请求头配对。分成两个域名要重做 CORS 与跨站 Cookie，本方案不做。
- 后端单实例即可；若要多实例，先看 §5.3 的“多实例启动顺序”。

## 3. 服务器前置条件

| 组件 | 要求 | 检查命令（只读） |
|---|---|---|
| JDK | **21**（项目 `java.version=21`）。本机开发机默认是 17，部署机别照搬 | `java -version` |
| MySQL | 8.4（迁移脚本针对 8.4 与 H2 兼容模式编写；列级 `COLLATE utf8mb4_0900_as_cs` 是 MySQL 8 专有） | `SELECT VERSION();` |
| Nginx | 支持 `http2 on;` 的版本（1.25.1+）。示例用的 `limit_req_zone` 要写在 `http` 级 | `nginx -v` |
| 时区 | 服务器与 JVM 用 UTC 或明确的时区；连接串已带 `serverTimezone=UTC`。AI 每日额度按 **UTC 日期**重置（北京时间 08:00） | `date` |
| 端口 | 后端只监听 `127.0.0.1:8080`；对公网只开 80/443 | `ss -lntp` |

构建机（可以是你本机或 CI，不必是服务器）：Node 22+、npm、JDK 21、Maven 3.6+。

## 4. 配置清单（环境变量）

写在服务器上的环境文件里（模板见 `deploy/env/typeme.env.example`，权限 `600`，属主为运行用户），由 systemd 的 `EnvironmentFile=` 载入。**不要写进命令行参数**（会出现在 `ps` 里）。

| 变量 | 必填 | 说明 |
|---|---|---|
| `TYPEME_DB_URL` | 是 | 形如 `jdbc:mysql://<host>:3306/<DB_NAME>?useSSL=true&serverTimezone=UTC&characterEncoding=UTF-8`。**开发默认的 `useSSL=false&allowPublicKeyRetrieval=true` 不要带到生产**；跨主机连接请开 TLS |
| `TYPEME_DB_USER` / `TYPEME_DB_PASSWORD` | 是 | 专用账号，权限见 §5.1 |
| `TYPEME_CAPTCHA_SECRET` | 是 | 注册验证码签名密钥，**≥32 位随机串**（如 `openssl rand -base64 48`）。缺失则注册返回 503（失败关闭）。多实例必须相同；更换后在途的验证码立即失效（可接受，用户点“换一张”） |
| `TYPEME_TRUSTED_PROXIES` | 是（有反代时） | Nginx 的地址或网段，如 `127.0.0.1`。**不配则所有人共用一个限流桶**，一个攻击者就能锁死全站注册与登录 |
| `TYPEME_SETTINGS_SECRET` | 开 AI 且要在后台保存 Key 时 | ≥16 位；缺失时后台“写入 apiKey”返回 503。**轮换会让已存的 Key 无法解密**，需在后台重填 |
| `TYPEME_ADMIN_BOOTSTRAP_USERNAME` / `TYPEME_ADMIN_BOOTSTRAP_PASSWORD` | 仅首次建管理员时 | 用户名 4–32 位字母数字下划线；密码 12–72 位可打印 ASCII。**首次成功后立刻从环境文件移除密码**（用户名可留） |
| `TYPEME_PBKDF2_ITERATIONS` | 否 | 默认 210000。调低会削弱抗爆破能力，调高会增加每次登录/注册的 CPU；改动前在目标机上压测 |
| `TYPEME_AI_ENABLED` | 否 | 默认 `false`。AI 关闭不影响基础测评与固定报告 |
| `TYPEME_AI_BASE_URL` / `TYPEME_AI_API_KEY`（或 `DEEPSEEK_API_KEY`） | 开 AI 时 | 真实调用与个人数据外发**须用户授权**。`TYPEME_AI_MOCK_MODE=true` 仅用于演示，响应会标注 |
| `TYPEME_AI_*` 其余 | 否 | 额度、预算、超时，见 `application.yml`。**Nginx 的 `proxy_read_timeout` 必须 ≥ AI `request-deadline`（默认 90s）**，示例已设为 120s |
| `TYPEME_ILLUSTRATION_ALLOWED_HOSTS` | 否 | 插画图片域名白名单，默认是仓库里写的 COS 域名；换 CDN 要同步改 |

**启动命令**（systemd 里同样）：

```
java -jar /opt/typeme/typeme-backend-1.0.0.jar \
  --spring.profiles.active=prod --server.address=127.0.0.1 --server.port=8080
```

> 不要加 `ai` profile 当作开关：AI 是否启用以 `TYPEME_AI_ENABLED` 与后台设置为准（数据库设置优先于环境变量）。

## 5. 数据库方案

### 5.1 库与账号（由 DBA 或用户授权后创建）【需授权】

- **专用库**，字符集 `utf8mb4`，库默认排序规则 `utf8mb4_0900_ai_ci`（迁移里对需要区分大小写的列已显式写了 `COLLATE ..._as_cs`，别改库默认值）。**同实例上还有别的业务库时，迁移脚本里没有也不允许出现 `CREATE DATABASE` / `USE` / 跨库语句**，所以库必须先建好、连接串指向它。
- **专用账号**，只授权这一个库，不用 `root`。当前后端用同一账号跑 Flyway 和业务，所以账号需要：

  ```
  GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
        ON <DB_NAME>.* TO '<app_user>'@'<来源地址>';
  ```
  迁移脚本中没有 `DROP`（只在注释里出现过）。Flyway 自己要建 `flyway_schema_history`，`CREATE` 已覆盖。**不要授予 `DROP`、`GRANT OPTION`、全局权限。**
- 想把“迁移账号”和“运行账号”分开：当前配置不支持（Flyway 复用同一数据源）。要拆需要改配置并走评审，本手册不涉及。

### 5.2 数据库里有什么（便于核对）

迁移 V1–V11，共 19 张业务表 + `flyway_schema_history`：

| 迁移 | 内容 |
|---|---|
| V1 | `app_user`、`account_recovery_code`、`app_user_session` |
| V2 | `assessment_package`、`assessment_attempt`、`assessment_answer` |
| V3 | `assessment_report`、`report_self_reflection` |
| V4 | `ai_analysis_job`、`ai_consent`、`ai_usage_budget` |
| V5 | `api_idempotency`、`account_deletion_job`、`rate_limit_bucket` |
| V6 | `typeme_ai_setting`（含后台保存的、加密后的 AI Key） |
| V7、V8 | 给 AI 任务加用户备注列；放宽凭据 hash 列宽度 |
| V9 | `registration_invitation`（邀请码，**现已不被注册流程使用，保留**）、`admin_bootstrap_lock`、`app_user.ai_daily_limit` |
| V10 | `illustration_asset`（含 `INSERT IGNORE` 的初始插画地址数据） |
| V11 | `registration_captcha_used`（验证码已用令牌，本次新增） |

敏感度：`app_user`（用户名/昵称/密码 hash）、`account_recovery_code`（恢复码 hash）、`assessment_answer`/`assessment_report`（作答与报告）、`typeme_ai_setting`（加密后的 Key）。备份文件按同等敏感度保管。

### 5.3 应用启动时会自动写库的事（务必知道）

后端用 `prod` profile 启动后，在接受请求之前依次会：

1. **Flyway 迁移**：对 `TYPEME_DB_URL` 指向的库执行所有未应用的迁移（`validate-on-migrate=true`，`baseline-on-migrate=false`）。
2. **内容包登记**：`JungPackageRegistrar` 按 packageId upsert 当前内置的十六型内容包到 `assessment_package`。已绑定的内容包不得被静默替换——内容变更前先看契约与 `docs/2026-09-16/implementation/_contracts/`。
3. **首个管理员**：仅当“库里没有未删除的管理员”且“环境里用户名、密码都给了”时创建一个；已有管理员时不创建、不改密码、不提升同名普通账号；同名普通账号存在则拒绝并报错。多实例靠 `admin_bootstrap_lock` 串行。
4. **定时任务**：注销清理、AI worker、幂等记录清理、**注册防刷过期数据清理**（本次新增，每小时，删过期验证码记录和 24 小时前的限流桶）。

因此：**第一次把新版本连到现有库启动，就等于执行了迁移。** 要在受控窗口里、拿到授权后进行。

**多实例启动顺序**：先只启动 1 个实例，确认迁移与登记完成、日志无错，再启动其余实例。

### 5.4 按现场状态选择路径

先做 **【只读】** 的状态判断（用专用账号或 DBA 提供的只读账号）：

```sql
SELECT VERSION();
SHOW DATABASES LIKE '<DB_NAME>';
SELECT COUNT(*) AS tables_in_db
  FROM information_schema.tables WHERE table_schema = '<DB_NAME>';
-- 若存在 flyway_schema_history：
SELECT installed_rank, version, description, success, checksum, installed_on
  FROM <DB_NAME>.flyway_schema_history ORDER BY installed_rank;
```

| 场景 | 判断 | 做法 |
|---|---|---|
| **A 空库** | 库存在，`tables_in_db = 0` | 备份可跳过（无数据）；授权后直接启动，Flyway 从 V1 建到 V11。→ §6 |
| **B 已有 TypeMe 库，历史表齐全** | `flyway_schema_history` 存在、所有行 `success=1`、最高版本 ≤ 11 | **先备份并验证恢复**，再授权启动，Flyway 只补缺的迁移。→ §5.5、§6 |
| **C 已有库但迁移失败过** | 有 `success=0` 的行 | **停止。** 不要重试启动，不要 `repair`。向用户汇报；由用户/DBA 决定是人工修复还是从备份重建 |
| **D 非空但没有 `flyway_schema_history`** | `tables_in_db > 0` 且无历史表 | **停止。** `baseline-on-migrate` 刻意关闭；需要人工判断这库是什么、能否基线化 |
| **E 库里是别的系统的表** | 表名与 §5.2 不符 | **停止并确认库名是否填错。** 绝不在别人的库里跑迁移 |

**场景 B 额外检查——V10 校验和风险**：V10（插画表）曾在尚无任何库应用过它的前提下被“原地修正”过（见 V10 文件头注释）。如果某个库在修正前就应用了旧版 V10，Flyway 会因校验和不符拒绝启动（`Migration checksum mismatch for migration version 10`）。

- 处理：**停止**，把报错和该库 `flyway_schema_history` 里 V10 那一行汇报给用户。是否 `repair`（会改历史表）或手工对齐，由用户决定并授权。Agent 不得自行 `repair`。
- 不确定时的预检（**只读**，可在构建机做）：对比库里 V10 的 `checksum` 与仓库当前文件算出的 Flyway 校验和；差异就是上述情形。

**场景 B 的版本差异提示**：
- 库在 V8 或以下：V9 会给 `app_user` 加列 `ai_daily_limit`（带 CHECK 约束）、建邀请码表和管理员锁表，并预置一行锁数据。`app_user` 很大时 `ALTER` 会持元数据锁，放在低峰窗口。
- 库已在 V9/V10：只会补 V10/V11（建新表，不碰旧数据，很快）。

### 5.5 备份与恢复【需授权才能对生产库做；演练用临时实例】

迁移前（场景 B 必做）：

```bash
# 在能连到库的机器上；密码走 ~/.my.cnf 或环境变量，不要写在命令行里
mysqldump --single-transaction --routines --triggers --set-gtid-purged=OFF \
  --default-character-set=utf8mb4 -h <host> -u <backup_user> <DB_NAME> \
  | gzip > typeme-<DB_NAME>-$(date -u +%Y%m%dT%H%M%SZ).sql.gz
sha256sum typeme-<DB_NAME>-*.sql.gz > typeme-<DB_NAME>.sha256
```

- 备份文件放到**不同于库所在盘**的位置，权限 `600`。
- **恢复演练是上线前置条件**：把备份恢复到一个临时库/临时实例（**不是**生产库），核对表数量与几张主表行数，再删掉临时库。没有演练过的备份不算备份。
- 恢复到生产库属于破坏性操作，必须用户逐次授权。

### 5.6 迁移后只读核验

```sql
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
-- 期望：1..11 全部 success=1
SELECT table_name FROM information_schema.tables
 WHERE table_schema = '<DB_NAME>' ORDER BY table_name;
-- 期望：含 registration_captcha_used、illustration_asset、registration_invitation 等
SELECT COUNT(*) FROM assessment_package;           -- 内容包已登记（>0）
SELECT COUNT(*) FROM app_user WHERE role = 'ADMIN' AND status <> 'DELETED';  -- 有管理员（首次部署后应为 1）
```

### 5.7 回滚与数据处置

Flyway 社区版**没有 down 迁移**。回滚分三层：

| 想回到 | 做法 | 授权 |
|---|---|---|
| 旧版应用（数据库保持新结构） | 换回旧 jar 重启。V9–V11 只新增表/列，旧版代码不读它们，不冲突；旧版仍读 `registration_invitation`（该表一直保留）。**旧版会恢复“注册需要邀请码”** | 应用部署授权即可 |
| 只撤销 V11 | `DROP TABLE registration_captcha_used;` 并删 `flyway_schema_history` 里 version=11 的行。**不建议**：新版应用再次启动会重建；除非确实要长期停用新版 | 【需授权】，且 DDL |
| 回到迁移前的数据 | 从 §5.5 的备份恢复。会丢失备份之后的所有注册与作答 | 【需授权】，逐次确认 |

遗留数据说明：`registration_invitation` 表（含指向 `app_user` 的外键）保留；账号注销流程仍会清理其关联（代码里 `AccountDataDeletionService` 的 “invitations” 步骤）。**本方案不 DROP 它们**，如要清理，另起增量迁移并走评审。

### 5.8 容量与运维

- `rate_limit_bucket`、`registration_captcha_used` 由清理任务维护；每天抽查行数，若持续增长说明清理没跑（看日志里“清理注册防刷过期数据”）。
- 连接池用 Spring 默认（HikariCP，10 个连接）。单实例够用；多实例时 `实例数 × 10` 不要超过库的 `max_connections`。
- 慢查询、磁盘、备份成功与否需要有人看；本手册不提供监控系统。

## 6. 部署 Runbook（按序执行，每步有门槛）

### 6.1 构建（构建机，不涉及服务器与数据库）

```bash
# 仓库根目录；先看工作区状态，别带进来无关改动
git status --short

# 1) 前端
cd frontend && npm ci && npm run build        # 含 vue-tsc 类型检查与图片地址检查，退出码必须为 0
# 产物：frontend/dist/

# 2) 后端：只打接口，不带页面
cd ../backend && JAVA_HOME=<jdk21> mvn -P api-only package -DskipTests
# 产物：backend/target/typeme-backend-1.0.0.jar
```

**门槛检查**（缺一不可，结果写进交付报告）：

- 完整测试：`mvn test '-Dtest=*,!AccountSqlDialectMySqlIT,!AiSqlDialectMySqlIT,!ConcurrencyMySqlIT'` 与 `npm test`（若运行 `npm test` 会先生成旧量表内容，注意工作区 diff）。这三个被排除的类会**自动建库/删库**，没有授权不要跑。排除后只能说“该子集通过”。
- 确认 jar 里没有页面：`unzip -l typeme-backend-1.0.0.jar | grep -c 'BOOT-INF/classes/static/'` 应为 0；且含 `V11__registration_captcha_used.sql`。
- 记录两个产物的 `sha256sum`，部署时核对。
- 已知与本次改动无关的前端失败：`illustrationAssets.spec.ts` 2 个用例（工作区里 `home-hero.webp`、`assessment-jung.webp` 被删除）。若仍失败，在报告里如实写出，不要“修”成通过。

### 6.2 服务器准备（【需授权】：涉及改服务器）

1. 建运行用户 `typeme`（无登录 shell），目录：`/opt/typeme/`（jar）、`/srv/typeme/frontend/`（静态文件）、`/etc/typeme/typeme.env`（600）。
2. 上传 jar、`frontend/dist/*`，核对 `sha256`。
3. 写 `/etc/typeme/typeme.env`（从 `deploy/env/typeme.env.example` 复制，填真实值）。
4. 安装 systemd 单元（`deploy/systemd/typeme-backend.service.example`），**先不 start**。
5. 配 Nginx（`deploy/nginx/typeme.conf.example` + 其注释里的 `typeme-proxy.inc`），`nginx -t` 通过后**先不 reload**，或 reload 到“维护页”。

### 6.3 数据库（【需授权】，按 §5.4 的场景）

1. 只读判断场景；场景 C/D/E 立即停下汇报。
2. 场景 B：备份 + 恢复演练通过后才继续。
3. 确认库与账号已按 §5.1 就绪。

### 6.4 启动与迁移（【需授权】：这一步写库）

1. 用户确认：目标库 `<DB_NAME>`@`<host>`、操作“启动后端并自动执行 Flyway V1–V11、登记内容包、创建首个管理员（如配置）”。
2. 窗口内：`systemctl start typeme-backend`；`journalctl -u typeme-backend -f` 观察。
3. **成功标志**：日志出现 Flyway 迁移成功信息、`Started TypeMeApplication`、无 ERROR/堆栈；§5.6 的只读核验全部符合。
4. **失败处理**：任何 Flyway 报错（校验和不符、迁移失败、权限不足）→ `systemctl stop`，保留日志，汇报，**不要反复重启**（反复重启可能在半成品状态上叠加失败）。
5. 管理员创建成功后：编辑 `typeme.env` 删除 `TYPEME_ADMIN_BOOTSTRAP_PASSWORD`，`systemctl restart typeme-backend`（此时库里已有管理员，不会再建）。

### 6.5 切流量与上线后验证

1. `nginx -t && systemctl reload nginx`。
2. 验证清单（用 `curl`，注意不要在报告里贴 Cookie/Token）：

| 检查 | 预期 |
|---|---|
| `curl -sI https://<域名>/` | 200，`index.html` 带 `Cache-Control: no-cache` |
| `curl -s http://127.0.0.1:8080/actuator/health`（本机） | `{"status":"UP"}`；公网 `https://<域名>/actuator/health` 应 404 |
| `curl -s https://<域名>/api/v3/auth/csrf` | 200，JSON 含 token；响应头 `Set-Cookie: XSRF-TOKEN` |
| `curl -s https://<域名>/api/v3/auth/captcha` | 200，`image` 以 `data:image/png;base64,` 开头；**503 说明密钥没配上** |
| 连刷 `/api/v3/auth/captcha` 超过 Nginx 阈值 | 出现 429（说明 Nginx 限流生效） |
| 浏览器打开首页、`/#/register` | 页面正常；验证码图显示、可“换一张”；320/390/1440 宽度无溢出（需真实浏览器，截图脱敏） |
| 用管理员登录 `/#/admin/members` | 能看到成员列表，**没有邀请码区块** |
| Cookie | 登录后会话 Cookie 带 `Secure; HttpOnly; SameSite=Lax` |
| 限流按真实 IP | 从两个不同外网出口各取一次验证码并观察，限流计数互不影响；或在后端日志确认 `rate-limited` 日志里不是同一个内网地址 |

3. **真实注册流程验证会写库**（建账号 + 8 个恢复码）。要做就先得到授权，并事后走“账号注销”流程清掉测试账号；不要直接 `DELETE` 表数据。

### 6.6 上线后

- 观察日志 24 小时：`RATE_LIMITED`、`NOT_CONFIGURED`、Flyway/连接池报错、`清理注册防刷过期数据`。
- 注册被刷的信号：全站注册总量熔断（默认 60 次/小时）被频繁触发，或同一网段验证码通过率异常高。处置：调小 `typeme.ratelimit.registration.*` 对应环境配置并重启；仍无效则在 Nginx 层封网段，或评估换第三方验证码（见防刷方案 E-11）。

## 7. 回滚 Runbook

1. 应用异常：`systemctl stop typeme-backend` → 换回上一版 jar → `start`。数据库保持新结构（见 §5.7 第一行）。注意旧版会恢复邀请码注册，需要告知用户。
2. 前端异常：把上一版 `dist` 放回 `/srv/typeme/frontend/`（部署前保留上一版目录，如 `frontend.prev/`）。
3. 数据异常：走 §5.7 第三行，【需授权】。
4. 回滚后在交付报告里写明：回滚到哪个版本、数据库状态、哪些用户可见行为变了。

## 8. 常见故障速查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 启动失败，缺少 `TYPEME_DB_URL` | 没带 `--spring.profiles.active=prod`，或环境文件没被 systemd 读到 | 检查单元里的 `EnvironmentFile=` 与 profile 参数 |
| 连到了 `typeme_dev` / `root` | **没用 prod profile，走了开发默认值**（严重，立即停止） | 立刻 stop，检查是否对错误的库跑了迁移，汇报 |
| `Migration checksum mismatch for migration version 10` | 库里应用过旧版 V10 | 见 §5.4 场景 B，停止并汇报，不得自行 repair |
| `Found non-empty schema(s) without schema history table` | 场景 D | 停止并汇报 |
| 注册页验证码一直加载失败，接口 503 | `TYPEME_CAPTCHA_SECRET` 未配或少于 32 位 | 补密钥后重启 |
| 所有用户都被 429 | 未配 `TYPEME_TRUSTED_PROXIES`，限流都算在 Nginx 地址上 | 配置后重启；确认 Nginx 传了 `X-Forwarded-For` |
| 登录后立刻变未登录 | Cookie `Secure` 在 http 下不回传，或前后端不同域 | 确认全程 https、同域 |
| 报告页提示 AI 不可用 | AI 未启用/未配 Key，属正常降级 | 基础测评与固定报告不受影响 |
| AI 请求被网关掐断 | `proxy_read_timeout` 小于 AI deadline | 调到 ≥120s |

## 9. 交付报告模板（部署 Agent 完成后给用户）

- 部署的 git 提交/工作区状态、两个产物的 sha256。
- 实际执行了哪些验证、退出码；**没执行的**（真实浏览器、真实 MySQL 测试、真实 AI 调用、真实注册）逐项写“未执行”。
- 数据库：目标库、所属场景（A/B）、迁移前后 `flyway_schema_history` 的最高版本、备份文件位置与恢复演练结果。
- 配置：哪些变量已设置（只写“已设置/未设置”，不写值）。
- 遗留风险：网络层大流量攻击需 CDN/WAF；图形验证码抗打码平台有限；`registration_invitation` 表保留未清理；前端构建仍依赖仓库内的 `scripts/gen-fallback-content.mjs`。
