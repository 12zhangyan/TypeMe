# 注册验证码与防刷 开发方案

> 状态：实施中（Q-1 已裁决：图形验证码；Q-2 已裁决：下线邀请码入口；用户另要求“前端独立部署”，作为后续单独一步） ｜ 日期：2026-10-27 ｜ 基线：git main@9b47c7e（工作区仅有图片删除与未跟踪目录，无注册相关未提交改动） ｜ 来源：用户原话「注册方式不要改为邀请制，而是验证码的那种，同时要做到防止恶意刷注册、攻击网站」
> 实施范围：`backend/` 账号与安全模块、`frontend/` 注册页与 API/store、新增增量迁移（仅准备，不执行）、契约文档 §7.2。额外限制：不引入新依赖，不调用任何外部验证码服务，不收集邮箱/手机号。

## 执行卡片
- 改变：注册不再需要邀请码，改为在注册页填写站内生成的图形验证码；验证码在任何 PBKDF2 / 写库之前校验；注册链路补上分层限流（验证码签发、验证码尝试、通过验证码后的注册、全站总量）与过期数据清理。
- 保持：注册后的 8 个恢复码、免责声明同意、CSRF、会话建立、`409` 用户名冲突、登录/恢复现有限流与响应语义不变；已有账号与历史迁移（含 V9）不改；IP 解析仍只信 `trusted-proxies` 白名单。
- 先核验：① 生产部署是否在反向代理后、`TYPEME_TRUSTED_PROXIES` 是否已配（见 E-9，不配则全站共用一个 IP 桶，限流会误伤所有人）；② 部署镜像里 Java AWT 能否画出文字（字体，见 E-10）。任一不符先停下报告。
- 首个切片：S-1（后端：签发 + 校验 + 注册接入，一条最小完整路径，可用 MockMvc 走通）。
- 完成判据：A-1…A-12。

## 背景与目标
- 背景：注册当前是**必须邀请码**（E-1）。用户明确不要邀请制，改要验证码；同时担心被脚本批量注册拖垮站点。批量注册的真实代价在服务端：每次注册 1 次密码 PBKDF2 + 8 次恢复码 PBKDF2（各 210000 次迭代）加 10 行写库（E-2），所以防线必须放在这些开销之前。
- 目标：真人填一次图形验证码即可注册；脚本批量注册要么被验证码挡下，要么被限流/总量熔断卡住，且被挡的请求不消耗 PBKDF2。
- 非目标：
  - 不做邮箱/短信验证码（E-5）；不接第三方验证码（Q-1）。
  - 不改登录、恢复、AI 的限流口径。
  - 不解决网络层洪泛（L7 DDoS）：应用内限流本身每次请求都要写库，挡不住大流量，需要边缘层（Nginx `limit_req` / CDN / WAF），见「兼容、风险与回滚」。
  - 不删除 `registration_invitation` 表、不写 DROP 迁移（Q-2）。

## 方案

### 注册请求的校验顺序（先便宜、后昂贵）
```
POST /auth/register
 1. @Valid 字段格式校验                              （已有）
 2. 来源 IP 的「注册尝试」预算（宽松）                （新增，按 IP 计数）
 3. 验证码校验：令牌签名/过期 → 按 nonce 错误计数 → 答案比对 → 烧掉 nonce   （新增，均不做 PBKDF2）
 4. 通过验证码后的 IP 注册预算（严格，沿用现有 5/小时）  （现有 checkRegisterIp 后移到第3步之后）
 5. 全站注册总量熔断                                  （新增）
 6. AccountService.register：免责声明、建号、8 个恢复码（唯一的昂贵部分，且不再接收邀请码）
```
第 2 步让「刷验证码」本身也有上限；第 4 步保持真人体验——填错验证码不会占掉严格预算。

### 验证码
- 签发 `GET /api/v3/auth/captcha`：响应 `{ token, image, expiresInSeconds }`（`image` 为 `data:image/png;base64,…`），`Cache-Control: no-store`。5 位字符，字母表去掉易混淆的 `0/O/1/I/l`，不区分大小写；有效期 3 分钟（假设值，可配）。按 IP 限流（默认 60 次/小时，覆盖正常"换一张"）。
- 令牌：`base64url(nonce‖expiry) . base64url(HMAC)`；比较用常量时间；服务端不保存答案明文。
- 校验失败的对外语义统一：`400 VALIDATION_FAILED`，字段 `captchaAnswer`，文案「验证码不对或已过期，请换一张再试」。不区分"过期/错/已用"，避免给脚本分类信号；令牌被错 3 次作废时文案同上。
- 注册请求新增 `captchaToken`、`captchaAnswer`，删除 `invitationCode`。Spring Boot 默认忽略未知 JSON 字段，旧客户端多带 `invitationCode` 不会报错（仓库里只有 `ContentService` 自建的 mapper 开了严格模式，不作用于 MVC 请求体；`application.yml` 无 jackson 覆盖）。

### 数据与清理
- 增量迁移 `V11__registration_captcha_used.sql`：`registration_captcha_used(nonce CHAR(32) PK, used_at DATETIME(6), expires_at DATETIME(6))` + `expires_at` 索引。**仅准备文件，执行迁移受数据库授权约束。**
- 新增清理任务：定时删除 `registration_captcha_used` 过期行与 `rate_limit_bucket` 中窗口早已过去的行（分批删除，沿用 `IdempotencyCleanupJob` 的写法与 ISO-8601 间隔配置；失败只记日志）。

### 前端
- `RegisterView`：删除邀请码输入与相关文案；加入验证码区——图片、输入框、「换一张」按钮。
  - 进入页面加载；加载失败显示明确错误和重试，**不静默**；加载中按钮禁用。
  - 任何一次提交返回（成功之外）都**自动换新验证码并清空答案**，因为旧码已被烧掉；过期前主动换新。
  - 429 显示"稍后再试"并带 `retryAfterSeconds`（沿用 `FormErrorNotice`）；503 显示"暂时无法注册"。
  - 防重复提交沿用 `auth.busy`；离开页面清理定时器。
  - 图片带 `alt`，输入框有 label，键盘可达；320 / 390 / 1440 宽度验证。
- 同步：关于页「本站采用邀请注册」改为实际口径；`v3.ts` 的 `FIELD_LABELS`、注册类型与 `auth.ts` 的 `register` 参数；契约 §7.2 新增接口与字段。

## 兼容、风险与回滚
- **发布顺序**：先部署后端（新接口 + 注册接受验证码，同时**忽略**邀请码字段），再部署前端。反过来会出现新前端带验证码、旧后端仍要邀请码的窗口。上线前先把 `TYPEME_CAPTCHA_SECRET` 注入（≥32 字符）；没配会是 503，而不是放开。
- **迁移**：V11 仅新建表，可回滚（删表）；执行迁移与任何 DDL 需要用户对具体库的授权，本方案不执行。
- **回滚**：回退应用版本即可恢复邀请制（旧版本仍读 `registration_invitation`，该表本期不动）；V11 的表留着无害。
- **未覆盖的攻击面**：
  - 网络层大流量洪泛：应用内限流每次请求都要写库，挡不住；需要在 Nginx/CDN 层做 `limit_req`、连接数与 WAF 规则。本方案不含，建议部署时补。
  - 验证码被 OCR/打码平台破解：只能靠 IP 预算和总量熔断兜底；升级路径见 E-11 与 Q-1。
  - 视障或看不清的用户：图形验证码无语音替代，只能"换一张"。若有需求需另行设计（Q-1 的第三方方案通常自带无障碍通道）。
  - 总量熔断可被攻击者用来挤占真人（E-12）：被挤占时 429 有提示，运维可临时调大额度；这是已接受的取舍。
- **日志**：不得记录答案、令牌、IP 明文之外的账号信息；沿用 `SecurityLoggingDisciplineIT` 的日志纪律。
