## 现象与影响

- 期望：同一浏览器里 A 退出、B 登录后，A 会话发出的任何请求在返回后都不能改变 B 的登录态、资料、页面结果，也不能以 B 的身份被重发。
- 实际（三类表现，均已复现）：
  1. A 会话迟到的 401（或 401 错误正文迟到）触发全局"会话失效"，把刚登录的 B 清成未登录，页面回到登录页并提示"登录状态已经失效，请重新登录"。
  2. A 发起的写请求（如改昵称）遇到 `CSRF_INVALID` 时，前端按契约"刷新 token 重试一次"，但刷新拿到的是 B 会话的 token，重试请求带着 B 的 Cookie 发出；等待 CSRF token 期间换号的 A 写请求，也会在换号后才以 B 的身份首次发出。
  3. A 的 `/me` 个人资料响应或导出正文晚到时，被 `applyProfile` / 导出流程交给当前（B）页面：B 账号上显示 A 的资料，导出可能把 A 的文件交给 B 的页面下载。
- 连带问题：A 旧动作的 `finally` 把 B 正在登录时的 `busy` 提前置为 false；量表目录 `reset()` 不解除旧 `loading`，B 无法立即重新加载目录，旧结果/错误还会覆盖新状态；CSRF 缓存清理后，旧的在途 token 获取仍会写回缓存或清掉新请求的合并状态。
- 影响对象：同一浏览器标签内先后使用两个账号的用户（共享设备、测试换号、退出后立即换号）。需要"A 有请求在途 + 在它返回前完成退出并登录 B"的时序，属于低频竞态。
- 严重度判断：涉及账号间数据串显示与"以 B 身份执行 A 的写入"，属于账号隔离/安全边界问题，优先级高于一般体验缺陷。
- 复现状态：通过可控延迟的 mock 网络单测与"构建产物 + Chromium + 合成网络"浏览器脚本稳定复现；没有生产日志、用户报障记录或真实后端复现证据。

- 已证实事实：前端请求层和 auth/目录 store 在"会话切换"时没有任何请求归属标识，异步回调（响应、错误正文、CSRF 重试、`finally`）一律作用于回调执行时的全局状态。
- 根因（已证实）：请求与本地会话之间缺少"发起时会话版本"的绑定。具体机制：
  - 迟到 401 → `notifySessionExpired` → 会话桥在 B 已登录时执行 `applyAnonymous`，清掉 B。
  - `CSRF_INVALID` 重试 / 等待 token 的写入 → 浏览器自动附带当前（B）的会话 Cookie，`ensureCsrfToken` 取到 B 的 token，于是 A 的写入以 B 身份发出。
  - 迟到的成功正文 → `refreshProfile` / `exportData` 直接采用，A 的资料或导出交给 B 页面。
- 推断影响（未验证）：CSRF 重试或延迟写入在真实后端会被当作 B 的合法请求处理，A 的修改（如昵称）可能落到 B 账号上。证据中的 mock 只证明前端发出了第二次写入，未验证真实后端持久化结果。
- 已排除解释："所有 401 都不该退出"不成立——当前会话 401 的对照用例在修复前后均通过，修复只针对旧会话请求。
- 未排除但无证据支持：后端会话或 Cookie 归属缺陷。纯前端 mock（无后端）已能独立触发全部现象，因此后端缺陷不是必要条件；本次未核验后端。
- 版本漂移 / 待确认：
  - "之前出现过串号"的现场来源仅为用户陈述，仓库内无生产日志或报障记录；无法确定现场版本与发生次数。
  - `2302f11` 是否已部署到线上未核验；源码已修复不等于线上已修复。

## 修复方式（已落地，`2302f11`）

- `frontend/src/api/v3.ts`
  - 新增模块级 `sessionRevision`、`invalidateSessionRequests()`（自增版本并清 CSRF 缓存）、`assertSession()`、`assertResponseSession()`，以及 `WeakMap<Response, revision>` 记录每个响应所属会话（约 52–71 行）。
  - `request()`（约 532 行）在发起时捕获版本；`send()` 发出前、网络异常后、拿到响应后、读取错误正文后、CSRF 重试发出前后都校验；不一致时抛 `SESSION_CHANGED`，不再调用 `notifySessionExpired`，也不进入重试。
  - `readJson()`、`ignoreBody()`、`exportAccountData()` 在正文读取完成后再校验一次，拒绝换号后才到达的正文。
- `frontend/src/api/csrf.ts`：`clearCsrfToken()` 自增 `cacheRevision` 并丢弃 `inflight`；`fetchCsrfToken(revision)` 只在版本未变时写回缓存，旧请求的 `finally` 不清除新的合并 promise。
- `frontend/src/stores/auth.ts`
  - `applyProfile` 在 userId 变化时、`applyAnonymous` 与 `reset` 总是调用 `invalidateSessionRequests()`。
  - `captureError` / `markCheckUnavailable` 忽略 `SESSION_CHANGED`，不写 `lastError`、不触发失效。
  - 各账号动作用 `operationRevision` 标记，只有最新操作的 `finally` 才清 `busy`；`logout` 的清理也只由所属操作执行。
- `frontend/src/stores/instrumentsV3.ts`：新增 `generation`；`reset()` 自增并解除 `loading`；`load` / `loadDetail` 的结果、错误和 `finally` 只在 generation 未变时写回。
- 用户可见结果：旧会话请求静默结束（`AccountView` 的 `run()` 吞掉异常，`lastError` 为空），B 不被退出、不显示 A 的数据、不下载 A 的文件；当前会话自身的 401 与 CSRF 重试行为保持不变。
- 修复边界：只改前端请求层与 store；不改后端鉴权、CSRF 契约（"CSRF_INVALID 重试一次"）和会话失效语义；已发出到服务端的旧请求不会被撤回。
- 回归风险与需同步检查的调用方：新增的 API/store 若绕过 `request()`（直接 `fetch`）将不受保护；新增账号动作需沿用 `operationRevision` 模式；其他有异步加载的 store 在 `reset` 时需同样失效旧回调。
