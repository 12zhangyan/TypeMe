## 1. 阈值政策：`0.20` 与 `0.10` 的差别不在分子，而在"触发"与"边界"是不是同一个量

> **已决（2026-09-18）**：批准「规则 D」——新增 `scoringVersion = typeme-jung48-score-v3`，
> `T(n) = B(n) = floor(2n/10)`，最终边界另要求 `n > 0`；新草稿默认绑定 `typeme-jung48-zh-v3`；
> v1/v2 规则与内容包**冻结**，未知计分版本在加载期报错。触发条件未变，**没有任何人多答题**。
> 决定记录见 `docs/2026-09-16/implementation/_contracts/01-新测契约-v1.md` §4.1（v1.2）。
> **这不是"更准"的改动**：`0.10` 仍然没有信度/效度依据，本次只是把两处不一致改一致、并让
> "跳过追问"不再改变"倾向是否算轻"。下面 §「已知事实」与实测表记录的是**决策前**的状态，保留以便追溯。

### 已知事实（决策前）

- 计分：`c = direction × (rating − 3)`，`S = Σc`，`n` = 有效数字回答数，`m = S/(2n)`。
- 决策前代码把两个量**分开**（`backend/src/main/java/com/typeme/jung/domain/JungScoringPolicy.java`）：
  - 澄清触发 `T(n) = floor(boundaryNumerator × n / boundaryDenominator)`（`2/10`，**v3 未改**）
  - 最终边界：v1/v2 `B(n) = max(0, T(n) − 1)`（**冻结**）；v3 `B(n) = T(n)` 且要求 `n > 0`
- 用途分工：`JungScorer.checkCoverage` 用 **T** 决定"要不要追加澄清题"；`JungScorer.score` 用 **B** 决定最终 `TENTATIVE`。状态优先级：覆盖不足 `NEEDS_REVIEW` → 任一维平分 `TIED` → 任一维边界 `TENTATIVE` → 否则 `REFERENCE`（三档优先级 v3 未改）。
- v1 与 v2 两个内容包的 `scoringPolicy` 都是 `boundaryNumerator=2 / boundaryDenominator=10`（`typeme-jung48-score-v1` / `-v2`）。
- 原产品/开发方案：产品方案 §5.2 用 `±0.20` 作**触发**；开发方案 §3.4 用 `5×|S| ≤ 2n`（≈`|m| ≤ 0.20`，即 `|S| ≤ floor(0.4n)`）作**边界**——原方案把同一个 0.20 同时当触发与边界。
- **契约 §4.1 有一处说明错误，已勘误（只改说明、不改规则）**：它写两种写法的差异"只出现在 `T(n)` 那一格（`n=12` 时 `|S|=2`、`n=16` 时 `|S|=3`）"，**这不成立**。原方案边界是 `|S| ≤ floor(0.4n)`、现行边界是 `|S| ≤ B(n)`，差异是**一整段区间** `B(n) < |S| ≤ floor(0.4n)`：`n=9` 时 `|S| ∈ {1,2,3}`、`n=12` 时 `|S| ∈ {2,3,4}`、`n=16` 时 `|S| ∈ {3,4,5,6}`。原文只举了该区间的下沿（恰好等于 `T(n)`）。
  出错的是**数学解释**，不是规则：`T`、`B` 的定义与"边界只在最终合并题集上判定一次"都不变，现行实现仍然是契约符合的。**"实现以冻结契约为准"只说明当前实现的依据，不能用来证明这段解释正确。** 勘误已写入 `01-新测契约-v1.md` §4.1 与 `阈值政策对比与决策请求.md` §1。

**本轮实测（TS 计分器 + v2 包，JP 维、其他三维明确、跳过补充题）**

| `n` | `S` | `m` | 原方案边界 `5\|S\|≤2n`？ | 触发 `T(n)` | 边界 `B(n)` | **当前实际状态** |
|---:|---:|---:|---|---|---|---|
| 12 | 1 | 0.042 | 是 | 2 → 是 | 1 → 是 | `TENTATIVE` |
| 12 | 2 | 0.083 | 是 | 2 → 是 | 1 → **否** | **`REFERENCE`** |
| 12 | 3 | 0.125 | 是 | 2 → 否 | 1 → 否 | `REFERENCE` |
| 12 | 4 | 0.167 | 是 | 2 → 否 | 1 → 否 | `REFERENCE` |
| 9 | 1 | 0.056 | 是 | 1 → 是 | 0 → **否** | **`REFERENCE`** |
| 9 | 2 | 0.111 | 是 | 1 → 否 | 0 → 否 | `REFERENCE` |

- **"触发"不等于"结论不确定"**：`n=12,S=2` 与 `n=9,S=1` 都会**被追问**，但最终仍是 `REFERENCE`。所以"追问变多"不自动等于"`TENTATIVE` 变多"——完成澄清题后 `S` 与 `n` 都会变，真实占比需要样本。
- `n=9` 时 `B(9)=0`：该维非零时永远不会被判"略偏"，只能是平分（`TIED`）或非边界。这是规则效果，不是经验结论。

### 可选方案

| 方案 | 触发 `T` | 最终边界 `B` | 优点 | 代价 |
|---|---|---|---|---|
| **A 保持现状** | `floor(0.2n)` | `max(0, T−1)` | 与 v1 一致，历史报告无需区分；`REFERENCE` 更多 | 小 `n`（如 9）下"略偏"不可能出现，与该标记的语义相反；边界附近的人可能拿到过度确定的表述 |

## 3. AI：把"协议行为"和"语言质量"拆开，别指望一次调用补齐

- **真实上游证据只有一条，且是旧契约时期**：`docs/optimization/verification/2026-09-18-ai-upstream-401/REPORT.md`（第 19 轮，`mockMode=false` + 故意写错的 key，真打到 `api.deepseek.com`，`errorCode=UPSTREAM_401`）。**未重跑**，且那时用的是 v2 提示词/契约。
- **v3 完全没有真实调用证据**：`docs/optimization/verification/2026-09-18-readable/REPORT.md` 自述"没有验证真实模型的语言质量、拒答／重试分布和成本"。

### 可选方案

| 方案 | 代价 | 能证明什么 |
|---|---|---|
| **① 保持 mock/受控故障证据** | 成本可控 | 本站行为；**不能**估算真实模型质量与发生率 |
| **② 受控真实试验（合成报告）** | 需要授权与费用；要约定目标分支、调用上限、预算、外发范围、停止条件 | 只能证明"在那次条件下走了哪条分支 + 那一次输出是否合格" |
| **③ 延后到运行观测** | 证据来得更晚，需另做脱敏观测方案 | 真实分布，但上线前没有依据 |

### 缺少的证据 / 明确的坑

- **一次真实调用补齐不了分支**：它不会分别产生 401、超时、截断，更不会产生 429 或坏 JSON。客户端短超时只能证明**本地截止行为**；人为限制输出长度只证明**该条件下**会截断——都不是自然发生率。
- **不要为凑证据去冲击上游限流**；也不要沿用历史文档对"401 不产生费用"的保证去推断其他分支的费用。
- 语言质量若要做，需要的记录是：绑定的 prompt/schema/model、合成输入摘要、实际输出、错误分类、重试次数、耗时与用量，以及**真人读一遍是否觉得误导**（AI 自评不算）。

### 我的建议

1. **协议层不必再花真实调用买证据**：已有「隔离 H2 + mock 下的确定性集成验证」，它证明不了的东西（自然发生率）本来也不是真实调用能补的；要补的是"绑定版本的记录整理"。
2. **语言质量层：如果要做，按"小样本真实生成 + 真人阅读判断"设计**，调用次数与预算留空待你定；不要把它写成"补齐失败分支"。
3. **优先级是我的建议、不是结论**：预算有限时，**③ 上线后脱敏观测**成本最低且样本最真实；**②** 只值得用于"上线前必须知道语言是否误导"这一具体问题。做不做、花多少，由你决定。
4. 无论选哪个，**现在就可以写清楚**：每个分支用户会看到什么（代码里已有），并标注"这一条来自隔离 H2 + mock 的确定性集成验证 / 这一条来自真实上游（历史 401，未重跑） / 这一条尚无证据"。

### 需要你决定的具体事项

对应 **决定三**（见 §4）：是否开展真实 AI 语言质量试验。调用上限、预算、外发范围与停止条件属于方案选定后的实施前置条件，不在现在追问。
